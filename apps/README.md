# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения
Разграничения по ролям пока нет, но полагаю, что обычный пользователь может тольк получать инфо с датчиков.
В задаче сказано, что установка новых датчиков требует выезда специалиста(наверное, он и есть администиратор).

**Управление отоплением:**
- Пользователи могут:
    - просматривать текущую температуру в помещении
    - выбирать нужное помещение и получать температуру оттуда
    - посмотреть статус датчика
    - узнать дату последнего обновления


- Администриторы могут:
    - создать датчик(`CreateSensor`)
    - посмотреть список датчиков(`GetSensors`)
    - посмотреть конкретный датчик(`GetSensorByID`)
    - изменить параметры датчика(`UpdateSensor`)
    - изменить показания и статус(`UpdateSensorValue`)
    - удалить датчик(`DeleteSensor`)


- Система обеспечивает:
    - сохранение датчик в бд с дефолтным статусом `inactive`(`CreateSensor`)
    - поиск списка датчиков(`GetSensors`)
    - поиск датчика по id(`GetSensorByID`)
    - обновление параметров датчика: название, тип, местоположение, единицу измерения, значение, статус(`UpdateSensor`)
    - установку новое значение температуры и статуса(`UpdateSensorValue`)
    - удаление датчика по id(`DeleteSensor`)

**Мониторинг температуры:**
- Пользователи могут:
    - просматривать текущую температуру в помещении
    - выбирать нужное помещение и получать температуру оттуда
    - посмотреть статус датчика
    - узнать дату последнего обновления


- Администриторы могут:
    - посмотреть показания всех датчиков(`GetSensors`)
    - посмотреть показание конкретного датчика(`GetSensorByID`)
    - посмотреть температуру в указанном месте(`GetTemperatureByLocation`)
    - узнать время последнего обновления(`LastUpdated`)
    - узнать состояние датчика(`Status`)


- Система обеспечивает:
    - получение датчиков из бд и получение актуальных данных с этих датчиков через внешнее api(`GetSensors`)
    - получение конкретного датчика из бд и получение его актуальных данных через внешнее api(`GetSensorByID`)
    - выполнение запрос по внешнему api для получения температуры в указанном местоположении(`GetTemperatureByLocation`)
    - получение время последнего обновления(`LastUpdated`)
    - получение статуса(`Status`)

### 2. Анализ архитектуры монолитного приложения

- Язык программирования: Go
- База данных: PostgreSQL
- Архитектура: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в
- рамках одного приложения. Код разделён на несколько пакетов:
- models — структуры данных;
- handlers — обработчики HTTP-запросов;
- db — взаимодействие с бд;
- services — бизнес-логика и взаимодействие с внешним API для получения температуры.
- Взаимодействие: Синхронное, запросы обрабатываются последовательно, REST API
- Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям.
- Развертывание: Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов
- Домены:
    - мониторинг температуры(получение, предоставление и отображение температурных показаний, отслеживание состояния
      датчиков и времени последнего обновления)
    - управление датчиками(регистрация датчиков, хранение их характеристик, изменение параметров и удаление записей.
      Предполагается, что эти операции доступными администратору)
    - интеграцию с внешним api: получение показаний из внешнего api, обработка ответов и ошибок при недоступности внешнего
      сервиса.

- Границы:
    - мониторинг температуры: отвечает за предоставление данных пользователю. При получении списка датчиков или отдельного
      датчика приложение пытается запросить актуальные показания через внешний api.
    - домен управление датчиками: отвечает за сохранённые сведения о датчиках. Изменение этих сведений не должно приводит
      к изменение температуры в физическом помещении.
    - домен интеграцию с внешним api: отвечает за интеграцию с внешним сервисом. Не определяет  права пользователя

### **4. Проблемы монолитного решения**

- сильная связность компонентов: изменение кода получения температуры может потребовать изменения обработчиков http-запросов
- сложность масштабирования: все компоненты работают в рамках одного приложения. Если количество запросов на мониторинг
  температуры значительно увеличится, потребуется масштабировать приложение целиком. Даже если остальные функции
  используются редко.
- зависимость от внешнего api: увеличение числа датчиков может привести к увеличению времени ответа, а сбои внешнего
  сервиса могут ухудшить работу мониторинга
- смешанная ответственность компонентов: обработчики http-запросов не только принимают запросы и формируют ответы, но и
  содержат логику получения актуальных показаний
- сложность тестирования
- проблема с разграничением доступа: например, пользователь, который может только смотреть
  температуру, не должен иметь возможность удалять датчики
- сложность развития предметной области: в приложении можно выделить несколько доменов: мониторинг температуры,
  управление датчиками и взаимодействие с внешним api. Но пока это не самостоятельные контексты
